# Multi-app restrictions — Phase 2

Daylock's existing AccessibilityService now enforces one shared Freedom state for explicitly selected Android apps. The service and Activity keep their existing component identities, so upgrading does not require a new Accessibility service or alter the app ID. The Settings and lock-screen designs remain in place; Today only changes the old Instagram-specific explanatory sentence to refer to app restrictions.

## Discovery and safety

`RestrictedAppCatalog` queries `PackageManager` for enabled, exported `MAIN`/`LAUNCHER` activities in the current Android profile. It deduplicates packages, sorts their real labels, and renders actual application icons at 64px for the Flutter picker. Missing icons use an explicit unavailable placeholder. The manifest declares scoped `LAUNCHER` and `HOME` intent queries; no `QUERY_ALL_PACKAGES`, Usage Access, device-admin, or new sensitive permission is requested. See Android's [package visibility guidance](https://developer.android.com/training/package-visibility/declaring).

The shared `RestrictedAppPolicy` rejects Daylock, Android system UIDs, persistent applications, non-launchable/disabled apps, and package identities for Android itself, system UI, Settings, the Android/Google permission controllers and package installers, and Keyguard. The catalog additionally resolves all HOME-capable packages, Android Settings, Accessibility/security/application-management, permission management, dial/emergency dial, uninstall and package-install handlers, and input methods, and excludes those identities. The service rechecks this same policy and the package's installation identity before a restriction, not merely when showing the picker. This is deliberately conservative; some launchable apps serving recovery or phone roles may be unavailable for selection. OEM-specific interfaces and Android profile/package-visibility behavior still require real-device verification.

## Persistence and migration

The Android `daylock.instagram_detection.v1` private preferences remain the sole authority. A separate versioned `restrictedApps.v1` record contains the selected package names, each package's `firstInstallTime`, a revision, and a count of selections removed as unavailable. The existing `nativeState` record continues to own the master switch and durable Freedom inputs. Flutter receives read-only snapshots and sends serialized per-package changes; it does not maintain a second persistent selection list. Writes use synchronous atomic preferences commits on the serial native worker, and UI feedback is optimistic while a write is pending. If discovery or persistence fails, enforcement pauses and an error is displayed; a refresh retries a pending explicit selection. Turning the master switch off remains possible.

When the new record is absent, migration runs once using the old master setting. If Instagram blocking was enabled, `com.instagram.android` is added with its current installation identity and the old master remains enabled. If it was disabled, the list starts empty and the master remains disabled. Existing Freedom inputs/settings are untouched. A missing or no-longer-supported legacy Instagram selection is removed during reconciliation and the picker displays a removal notice. The durable record prevents repeating the migration.

An uninstall removes the corresponding selection; replacing/updating a package retains its selection. Reconciliation and the installation timestamp also prevent a package reinstalled while Daylock was stopped from becoming selected automatically. A newly installed/reinstalled app must be explicitly selected. Android may filter package-change broadcasts; the startup/discovery reconciliation and the enforcement-time identity check remain in place. These native preferences retain the app's pre-existing backup exclusion and are not an export mechanism for moving selections to a new phone.

## Enforcement, privacy, and navigation

The master switch governs enforcement and remains distinct from Freedom Control. Only selected, currently supported installations enter the existing event gate; other windows invalidate pending foreground actions without storing an app history. Master-off selected-app openings are not recorded. The foreground guard distinguishes selected packages, coalesces repeat events, cancels stale navigation after rapid switches, and rechecks state revisions. The existing shared Freedom calculation, zero-eligible policy, recovery gate, Home/lock launch sequence, fallback throttling, notification channel and navigation flags are retained. If native Freedom inputs are unknown, the existing bounded recovery behavior applies: a recovery screen may be offered once for that state and subsequent openings are allowed until the state changes.

The Activity is non-exported and checks both its native attempt and current selected foreground identity. It resolves the displayed app name from PackageManager, never from an untrusted label extra. Return to Daylock, Home, Disable app restrictions, and Accessibility Settings remain available. The same notification channel and throttle are reused, with the selected app's trusted label in the fallback title. Permissions and Android channel settings still control delivery.

Only the most recent selected-app package, detection time, Freedom state and restriction result are stored locally for diagnostics. No installed-app list or foreground activity is uploaded, no history or usage analytics are introduced, and release builds suppress the debug foreground diagnostic log. Android's Accessibility service is voluntary and not tamper-proof; the user can revoke it or uninstall Daylock normally.

## Files

- `RestrictedAppsRepository.kt`, `RestrictedAppCatalog.kt`, `RestrictedPackagesReceiver.kt`: native selection authority, migration, safety/discovery and package/boot reconciliation.
- `DetectionStore.kt`, `DetectionRuntime.kt`, `MainActivity.kt`, `AndroidManifest.xml`, `detection_strings.xml`: existing native storage/bridge/consent extended with selections and accurate disclosures.
- `InstagramDetectionService.kt`, `DetectionPolicy.kt`, `InstagramLockFlow.kt`, `InstagramLockActivity.kt`, `InstagramLockFeedback.kt`: extend the existing service, guards, dynamic identity and fallback; internal legacy class/channel names are retained for compatibility.
- `lib/services/instagram_detection_bridge.dart`, `lib/screens/restricted_apps_section.dart`, `lib/screens/instagram_detection_section.dart`, `lib/screens/settings_screen.dart`: native channel, searchable picker, master control, status and diagnostics. `lib/design/daylock_freedom_status.dart` updates the outdated Instagram-only sentence.
- `RestrictedAppsTest.kt`, `RestrictedAppsInstrumentation.kt`, `restricted_apps_test.dart`, and updated existing tests: selection/migration, real Android discovery, foreground guard, UI, persistence and regression checks. `tool/android/build_multi_fixtures.ps1` creates three harmless emulator test apps, outside the Daylock APK.

## Pending physical-device checklist

1. Install the draft update over Daylock and confirm existing commitments, Freedom settings and Instagram preference remain intact. If Instagram was previously enabled and is still installed, check it appears selected and the master remains on; if it was off, check it has not been silently selected or enabled.
2. In Settings > Freedom Control > Restricted Apps, select Instagram and YouTube; check search, icons, count and persistence after closing/reopening Daylock. Leave a third ordinary app unselected.
3. With Freedom unearned and Accessibility connected, open each selected app from launcher and Recents, then the unselected app. Verify the correct name, no repeated loop, and test rapid switching and screen lock/unlock.
4. Deselect YouTube and verify it opens; select it again. Earn Freedom and verify both apps open. Change Freedom Time/commitments and ensure stopwatch time itself has not become a requirement.
5. Restart Daylock and the phone; unlock and wait for Accessibility to connect before checking restrictions. Test permission revocation, master-off behavior, and uninstall/reinstall of a selected app if appropriate.
6. Test Return to Daylock, Return Home, Disable app restrictions and Accessibility Settings. Verify Daylock, Android Settings, launcher and recovery interfaces remain usable.
7. Test the fallback with notifications denied and with its channel disabled/enabled; check it does not affect existing Plan, Commitment or Freedom alerts.

Physical-device behavior, OEM recovery-app exclusions, Android background launch restrictions and real Instagram/YouTube behavior remain unverified. Android may delay/disconnect Accessibility or reject a background Activity launch; Daylock cannot guarantee enforcement before the service connects, while the screen is locked, or after a force-stop. A fallback notification is subject to Android permission/channel settings. Keep the release in draft until phone testing is complete.
