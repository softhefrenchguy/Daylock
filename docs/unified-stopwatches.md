# Unified commitments and stopwatches

Each commitment can be checked off independently of its optional stopwatch. The old Goal/Focus fields are kept only as legacy metadata; no duration causes completion. Routine steps and existing plan locks continue to use their existing relationships and rules.

## Storage and recovery

The v2 state contains a stable commitment ID, accumulated milliseconds and, when running, a wall timestamp plus a monotonic anchor and clock session. Existing records receive deterministic IDs based on their date and position; previously stored IDs are retained. Before migrating an old v2 live plan, the exact original JSON is retained under `daylock.state.v2.before-stopwatch`. The v1 backup is also retained. Historical task maps are kept intact; original Focus targets and recorded time remain available. No time is inferred from a completion or a target.

Android samples `elapsedRealtime` and the system boot count over a small method channel; elapsed realtime includes deep sleep. A persisted anchor can be recovered across process termination within the same boot. Running time is projected from the monotonic clock; timer switches settle the previous commitment and save both changes in one state snapshot. Completion or excuse settles and stops the stopwatch. Timer and outcome actions are serialized. A failed save leaves the last durable snapshot unchanged, displays a retry, and prevents further timer transitions until a save succeeds. A sudden termination before a successful write can only restore the last durable state.

After a reboot, an unavailable boot identifier, an invalid or future monotonic anchor, or an unknown session, the stopwatch pauses and keeps only checkpointed time. Desktop and web use a process-local monotonic clock; a restart cannot recover an uncheckpointed segment. A pre-update running Focus timer has only a wall timestamp: migration credits a best-effort nonnegative interval of at most 24 hours, capped at local midnight, then starts a new anchor if still on the same day. Wall-clock changes during that legacy interval cannot be distinguished from elapsed time. For a live timer crossing midnight, history is capped at the old day's boundary. If the wall and monotonic intervals differ by over two minutes, only the checkpointed portion is archived, because the boundary cannot be reliably reconstructed. A repeated or conflicting persisted running timer is paused without crediting an overlapping interval. These conservative rules can omit uncertain effort; they never claim exact reconstruction after reboot or an unverifiable clock change.

## Freedom, notifications and Journey

Freedom retains its existing time, eligible completion, and tomorrow-plan conditions. Native persisted eligibility and notification policy no longer predict automatic completion from a legacy Focus deadline. The old Focus alert preference is retained in saved settings but no timer completion alert is scheduled. Other reminder categories and the Instagram blocker continue to use their existing channels and policies. Journey reads the same authoritative per-commitment accumulated duration, includes a live timer in its current projection, attributes it by Area, and retains actual time for incomplete and excused commitments. Historical dates are not duplicated by the live projection.

## Physical-device checklist

Use a test build signed with the existing app key and keep a backup before testing. Confirm the old Focus records, Area assignments, history, routine suggestions, and committed plans remain visible after upgrading. Verify immediate completion with no timer and Freedom only after all existing requirements are satisfied. Start, pause and resume a timer; switch rapidly between two commitments; complete and excuse a running timer; verify the saved duration and Journey totals. Background the app, lock the screen, switch apps and reopen after several minutes, then force-stop and reopen during the same boot. Test a reboot while running and check the conservative paused recovery. Test the day boundary, a clock adjustment, notification permission denied, and Instagram blocking/notification behavior with Freedom both earned and unearned. Confirm plan locks and routine accept/skip/dismiss and sequence behavior. Device-specific timing, system restrictions, and upgrade signing require physical verification.
